# F2 前端接入（可直接照着写）

后端已就绪，**不需要等任何人**：45 个 P0 接口全部可用，只有 P1（登出/解绑/推送等）未挂载。
本文给的是启动方式、固定契约和一条可跑通的"登录 → 看板"主链。可执行版本是
`python -m app.tools.demo_walkthrough`（会逐条打印请求与响应）。

## 1. 启动后端

```powershell
cd backend
$env:DATA_DIR = 'D:/vitasenior-demo'          # 空目录；删掉即完全重置
$env:MEDIA_TICKET_SECRET = '<至少16位随机串>'  # 媒体短链签名，别用示例值
$env:SCANNER_ENABLED = 'true'                  # 需要通知/到期结算时打开
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

- 本机地址：`http://127.0.0.1:8000`；手机调试用电脑局域网 IP，端口同上。
- 交互文档：`/docs`，机器可读契约：`/openapi.json`。
- 演示账号不用手工建：`POST /api/v1/demo/experiences` 每次生成一对老人/子女手机号。

## 2. 三条通用规则

1. 业务前缀 `/api/v1`。成功都是 `{"data": ..., "meta": {"request_id", "server_time"}}`；
   失败都是 `{"error": {"code","message","details","retryable"}, "meta": {...}}`。前端只认 `code`。
2. 除 `DEMO01`、`AUTH01/02`、`GET /health`、以及带 `ticket` 的 `MEDIA03` 外，都要
   `Authorization: Bearer <access_token>`。
3. **写接口要 `Idempotency-Key`**（任意唯一字符串，如 `crypto.randomUUID()`）。同 key 重放返回
   原结果；同 key 不同 body 返回 409 `IDEMPOTENCY_CONFLICT`。只读接口不需要。

### 常见错误码

| HTTP | code | 前端处理 |
| --- | --- | --- |
| 401 | `UNAUTHENTICATED` / `SESSION_EXPIRED` | 回登录页 |
| 403 | `ELDER_ACCESS_DENIED` / `PROPOSAL_REQUIRED` | 无权 / 子女写档案须走提案 |
| 404 | `NOT_FOUND` | 资源不可见（越权也返回 404，不泄露存在性） |
| 409 | `VERSION_CONFLICT` | 带 `details.current_version` 重新拉取再提交 |
| 409 | `BIND_CODE_*`、`CHANGE_ALREADY_APPLIED`、`ACTION_EXPIRED` | 按提示重试/新开流程 |
| 413/415 | `MEDIA_TOO_LARGE` / `MEDIA_UNSUPPORTED` | 图片 ≤10 MiB，音频 ≤15 MiB |
| 422 | `VALIDATION_ERROR` | 表单校验失败，`details.errors` 有字段路径 |
| 429 | `RATE_LIMITED` | 看 `Retry-After` |
| 501 | `MODULE_NOT_IMPLEMENTED` | 该入口未实现（当前 P0 全通，P1 会命中） |

### 真实理解模式下的两条硬要求

后端默认 `CHAT_PROVIDER=mock`；切到 `real` 后（见下方"启动真实理解"），`AGENT01` 的请求规则变了：

1. **不要传 `mock_fixture_id`**——它只在 mock 模式下有效，真实模式传了也不会伪造结果。
2. **文字必须含餐次和食物**，因为模型不能凭菜品猜餐别：`"今天午饭吃了青菜、豆腐和米饭"`。
   只发图片时，`context.scene` 必须是 `meal/ingredient/medicine/document` 之一，且仍建议附一句餐次文字。
3. 真实理解只覆盖**饮食记录**；用药/运动/提醒/绑定/档案会返回引导语（不伪造动作），继续用对应接口。

### 启动真实理解（可选，需要你自己的 key）

**推荐**：把凭据写进 `backend/.env`（已 gitignore），然后一条命令起服务：

```powershell
cd backend
.\run-demo.ps1              # 读 .env，起在 8000；-Port 8010 换端口
# 再到 /runtime 确认 providers.chat == "real"
```

`.env` 至少要有：

```ini
CHAT_PROVIDER=real
CHAT_API_KEY=<你的 MiMo key>
CHAT_BASE_URL=https://api.xiaomimimo.com/v1
CHAT_MODEL=mimo-v2.6-flash
```

也可以手工设环境变量（等价）：

```powershell
$env:CHAT_PROVIDER = 'real'
$env:CHAT_API_KEY  = '<你的 MiMo key>'
$env:CHAT_BASE_URL = 'https://api.xiaomimimo.com/v1'
$env:CHAT_MODEL    = 'mimo-v2.6-flash'
```

缺任一变量后端会**拒绝启动**（不会半 mock 半 real）。**应用不会自动读 `.env`**，只有
`run-demo.ps1` 会读并把变量导出给 uvicorn。

## 语音输入（ASR）与"一句话一轮"

真实 ASR 已接通（`ASR_PROVIDER=real`，`/runtime.providers.asr=="real"`）。前端按下面这条线接：

1. **录音格式**：服务端**不做 WebM 转码**。请直接采集 PCM 并封装 WAV，再走
   `POST /media`（`purpose=voice_message`，`mime=audio/wav`）。浏览器默认 `MediaRecorder`
   多半给 WebM/Opus——需要 `AudioWorklet`/`ScriptProcessor` 取 PCM 自己封 WAV，或在录音前就
   决定换格式（换格式属于范围变更，别静默改后缀）。
2. **一句话一轮**：说完那一刻取**一帧画面**，把 WAV + 这一帧图片通过 `MEDIA01` 上传，然后
   一次 `AGENT01` 带上 `audio_asset_id` + `image_asset_ids`。服务端先转写、再用该帧理解；
   持续摄像头预览 ≠ 持续上传视频。
3. **两种交互都支持**：
   - 想先给用户看/改转写：先 `POST /ai/asr {elder_id, audio_asset_id}` 拿 `transcript`，
     改完再用 `text` 调 `AGENT01`（此时**不要再**传 audio，避免重复识别）。
   - 想一步到底：直接把 `audio_asset_id` 交给 `AGENT01`，返回里 `turn.transcript` 就是转写。
4. **预算**：一次 Agent 轮次服务端按 45 秒总预算控制；ASR 约 1–3 秒。前端请求超时请大于 60 秒。
5. **边界**：转写**不会**直接产生饮食/服药事实，仍走"待确认 → 确认"；也请保留"识别可能有个别
   同音错字"的提示（实测会把"您好"写"你好"）。

## 4. 图片与语音播放（重要）

- 上传：`POST /media`（multipart：`file`、`purpose`、`elder_id?`），`purpose` 取
  `meal/ingredient/medicine/face/voice_message/agent_audio/document`。
- 响应里的 `content_url` 是**带 5 分钟票据的完整地址**，直接塞给 `<img src>` / `<audio src>` 即可，
  **不需要 Authorization 头**。过期就重新 `GET /media/{asset_id}` 换新地址。
- 音频素材来自服务端（提醒、提案播报），前端只负责播放并在**完整播完**后回执。

### 通知回执（60 秒窗口）

```
POST /elders/{id}/presence   {client_id:"web-1", visible:true}   # 页面可见时每 20 秒一次
GET  /elders/{id}/notifications                                   # 取待播报
POST /notifications/{nid}/events  {event_id:"<uuid>", event_type:"displayed"}
POST /notifications/{nid}/events  {event_id:"<uuid>", event_type:"answered"}
POST /notifications/{nid}/events  {event_id:"<uuid>", event_type:"playback_completed"}   # 每完整播一遍发一次
```

顺序必须 `displayed → answered → playback_completed`；`repeat_count=2` 就发两次
`playback_completed`（**每次新 `event_id`**，同 id 重放不累加）。只有完整播放才启动提案的 60 秒窗口，
播放本身**不等于**已服药。

## 5. 当前边界（别当成 bug）

- 所有 AI 都是 mock：`/runtime` 的 `providers` 会如实标 `mock`；未接入真实供应商。
- 提案播报只有 5 段精确匹配的预录语音（档案/提醒设置/用药新增/修改/停用）。不匹配时后端只保存
  **完整文字**、`audio_asset_id=null`，**不会启动 60 秒窗口**，前端要展示文字并允许直接接受/拒绝。
- 列表分页：`limit`(默认 20, 最大 100) + `cursor`，响应 `items`/`next_cursor`。
- 时间：请求用 UTC ISO8601（`2026-10-30T04:00:00Z`），业务日期 `YYYY-MM-DD` 按 Asia/Hong_Kong。
- 未挂载：登出、解绑、删计划、撤销提案、记忆导出、系统推送（P1）。
