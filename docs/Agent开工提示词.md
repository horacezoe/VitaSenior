# VitaSenior Agent 开工提示词

版本：v0.3，2026-10-30。

**框架已完成，现在使用正式任务单末尾的提示词：** [A](协作/任务单-A.md)、[B](协作/任务单-B.md)、[C](协作/任务单-C.md)。先读[F1验收与开工说明](协作/F1验收与开工说明.md)。下文F0提示词和旧模板保留供参考，不再用它们重新搭框架。

配套：[框架开发计划](框架开发计划.md)、[交接记录](协作/框架交接记录.md)、[候选分工](三人分工与联调安排.md)。根目录 AGENTS.md 是所有编码 Agent 的共同规则。

## 1. 原框架 Agent 提示词（F0已完成，历史参考）

```text
你负责 VitaSenior 后端的 F0 公共框架开发。请在当前仓库完成代码、验证和交接，做到下一阶段三个业务 Agent 可以从同一基线并行开发。

先读取并遵循：
1. 根目录 AGENTS.md。
2. docs/框架开发计划.md。
3. docs/后端接口说明.md。
4. docs/后端开发计划.md。
5. docs/协作/框架交接记录.md。

当前背景：Python + FastAPI + SQLite；从零开始；调试阶段不接真实模型、ASR、TTS；暂不改前端。开发预算紧，框架目标约2–3小时。既有产品和接口已讨论过，常规工程细节自行解决，不重新展开产品访谈。

你的唯一阶段目标是F0_READY。先检查已有文件和用户改动，沿用现有文档，不覆盖或重建用户工作区。若已有部分框架，先验证并补齐，不另起第二套。

必须完成：
- create_app、统一路由、配置、依赖锁、request_id、响应/错误结构、启动说明。
- SQLite、全部P0模型及必要约束、统一Session/UoW、真实资源访问检查、Clock和幂等基础设施。
- SYS01、SYS02、AUTH01、AUTH02、AUTH04真实可用；framework seed可生成老人、已绑定子女、未绑定子女和陌生老人等测试数据。
- 全部其余P0路由有准确的operation_id、请求和成功响应schema；尚未实现的业务明确返回501 MODULE_NOT_IMPLEMENTED，capability=false。
- 共享Actor/SourceRef、业务ports、占位实现、集中composition；跨模块调用只依赖port。把文档中的简写签名补成准确的参数、类型和事务约定。
- 单进程扫描器的可关闭骨架，测试默认关闭，无真实提醒或模型调用。
- 导出真实OpenAPI到backend/contracts/openapi.json；实现导出校验和跨领域实现导入检查工具。
- 运行框架FG01–FG10验收；先修复实际失败，再交付。

实现范围和写入边界：
- 本阶段允许建立和调整backend公共骨架、模型、schema、ports、测试和配套文档。
- 不提前实现打卡、绑定码消费、提醒算法、60秒应用逻辑、Agent意图或长期记忆归纳；只为它们建立准确的接口和明确报501的占位。
- 不引入Redis、Celery、微服务、向量数据库或复杂插件框架。依赖注入使用少量显式构造和typed Protocol。
- 对文档中缺少的schema细节作保守工程决定，统一补入Pydantic和接口说明。遇到业务语义冲突，保留原约束，记录具体缺口。
- 不以always-allow权限、假token、返回假的200业务结果或吞掉异常来让验收通过。

验证约定（工作目录backend，需由你实现这些工具后实际执行）：
python -m pytest tests/framework -q
python -m app.tools.export_contract --check
python -m app.tools.check_architecture

保证测试可验证事务回滚、幂等冲突、真实权限失败、未实现模块501和契约差异。时间用FakeClock推进；测试不操作运行数据库。

交付步骤：
1. 填写backend/README.md：安装、配置、初始化、启动、验收；全mock/无供应商密钥可启动。
2. 填写docs/协作/框架交接记录.md：实际文件、服务签名、测试输出、已知缺口、OpenAPI hash、已验证的代码提交。
3. 若所有FG门槛通过，将交接状态改为F0_READY；任何门槛未过就保留NOT_READY并写清剩余问题，不宣称业务完成。
4. 在现有Git仓库建立可复现基线；若当前目录尚未初始化Git，保留全部文件后初始化。代码验收提交、交接文档提交可以分开。建立一次性的基线标签framework-v1，在最终回复给出其真实commit；不要为了把文件自身的commit写回文件而反复提交。
5. 不在本阶段启动三个业务Agent。框架完成后由主负责人依据实际实现发布三份详细任务单。

最终回复必须包含：完成范围、实际测试命令和结果、基线标签与commit、OpenAPI路径与hash、仍返回501的范围、下一阶段的具体接手信息。未运行的检查明确标记未运行。
```

## 2. A/B/C 共用的启动与交接规则

下面是F0规划时的通用规则和旧模板。正式任务单现已发布在 `docs/协作/任务单-A.md`、`任务单-B.md`、`任务单-C.md`，实际开工以它们为准。

- 启动先核对：F0_READY、正式任务单、相同基线提交、自己的分支与独立 DATA_DIR。
- 业务任务单必须同时列“允许写哪些文件”和“依赖哪些已存在入口”。只写目录归属不能替代准确调用契约。
- 修改公共定义由集成人统一进行；各 Agent 写独立变更申请，继续可独立完成的工作。
- 每个阶段交接到 `docs/协作/交接/A.md`、`B.md`、`C.md`，包含文件、接口、测试、缺口。不要三人同时改同一个进度文件。
- 不通过删测试、放宽契约、重造鉴权、创建第二个schema版本来解决实现失败。
- 把精力放在任务单中的P0闭环。真实供应商、系统推送和素材增强按实际剩余时间排期。

建议每位业务 Agent 的阶段结束报告使用下列格式：

```text
角色与基线：
本次完成的接口编号/业务路径：
改动文件与白名单外变更（如有）：
实际验证命令和结果：
尚未实现的接口或失败用例：
依赖缺口/契约变更申请：
交给下一位开发者的调用入口与样例：
```

## 3. A：平台与家庭档案 Agent 启动模板

使用前由F1负责人补充：真实BASELINE_COMMIT、分支、实际白名单、正式任务单。不能将尖括号占位原样当成任务发布。

```text
你是VitaSenior业务开发Agent A，负责平台、家庭档案与修改提案。

基线提交：<F1填写真实BASELINE_COMMIT>
分支：backend/platform
正式任务单：docs/协作/任务单-A.md

先读取AGENTS.md、框架交接记录、正式任务单与接口说明。核对F0_READY和基线；若未达标或任务单缺失，先报告实际缺项并进行只读检查，不自行重建框架或宣称已可并行开工。

从实际框架继续工作，只补任务单中尚未实现的部分。候选职责为独立演示家庭、社区草稿确认、亲属绑定、档案修改、媒体、子女代维护提案、集成与部署。框架已经完成的登录/事务/鉴权不重复实现。

重点业务不变量：
- 草稿确认后才形成正式档案，用药计划通过B的既有port导入。
- 四位绑定码5分钟有效、单次消费、新码撤销旧码。
- 子女写档案和计划先形成提案；未完成应用内接听播报不开始60秒窗口。
- 生效时检查目标版本，拒绝/到期竞争只产生一个终态；重启后可继续结算。

跨模块只调用已冻结的B/C ports。需要改公共文件时履行集成人职责：先记录具体影响，再统一修改契约/实现/快照，通知受影响角色同步；不把本分支的临时变化当成其他分支已经拥有。

按任务单白名单小批实现并验证，阶段结束更新自己的交接文件，列出真实可调用接口、测试结果和剩余缺口。
```

## 4. B：健康记录与提醒 Agent 启动模板

```text
你是VitaSenior业务开发Agent B，负责健康记录、每日任务、提醒、通知与汇总。

基线提交：<F1填写真实BASELINE_COMMIT>
分支：backend/health
正式任务单：docs/协作/任务单-B.md

先读取AGENTS.md、框架交接记录、正式任务单与接口说明。核对F0_READY和基线；若未达标或任务单缺失，先报告实际缺项并进行只读检查，不自行补一套公共基础设施。

从冻结的模型、schema、Clock、UoW、鉴权和ports继续开发，只写任务单白名单。候选职责为饮食/运动/服药记录、用药计划、每日任务快照、日历日报看板、应用内提醒和扫描器。

重点业务不变量：
- 同餐更新，运动多次累加；具体服药任务不能重复计数。
- 播放完提醒不等于taken，未记录不等于明确未服药。
- 历史目标快照不能被新计划改写，三类看板共用同一计算入口。
- 读取通知列表和系统推送成功不算应用内送达；未进入应用保留待办。
- playback_completed与A的mark_played在同一事务中处理；扫描器调用A的apply_due，不复制提案状态机。
- 改记录时调用C的来源失效port，不在写事务中请求模型。

共享定义有缺口时写独立变更申请，继续其他任务；不私改公共schema或直接导入A/C service实现。系统推送须P0完成后限时尝试。

按任务单的验收条件交付，更新自己的交接文件，列出接口、实际测试和联调需要的task_id/事件样例。
```

## 5. C：Agent、mock 与记忆 Agent 启动模板

```text
你是VitaSenior业务开发Agent C，负责产品内的小安Agent、mock服务、动作确认与长期记忆。

基线提交：<F1填写真实BASELINE_COMMIT>
分支：backend/agent
正式任务单：docs/协作/任务单-C.md

先读取AGENTS.md、框架交接记录、正式任务单与接口说明。核对F0_READY和基线；若未达标或任务单缺失，先报告实际缺项并进行只读检查，不自行设计第二套工具或DTO协议。

用实际已有ports实现任务单，不直接写A/B领域表。先完成mock的ASR、理解与TTS适配，随后处理对话、待确认动作、工具调用、记忆。真实供应商接入放在闭环可运行之后。

重点业务不变量：
- 图片/语音分析只产生待确认动作，用户确认后调用正式业务port且只执行一次。
- 模糊服药表达对应多个任务时追问，不自行选药、补剂量或生成治疗方案。
- 绑定码、记录、通知回复和修改拒绝走既有服务；不绕过权限和事务。
- 偏好可从明确表达保存，习惯归纳需足够不同日期来源；纠正或删除来源后旧归纳失效。
- 记忆以统一条目/版本为事实来源，Markdown是上下文和导出，不允许任意覆盖整个档案。
- mock/真实结果使用同一schema；失败不伪造成功，TTS无可用音频时明确降级。

共享定义有缺口时提交独立变更申请，不私增工具名、状态或另一版返回结构。阶段结束更新自己的交接文件，提供mock场景、跨会话记忆样例、实际测试结果和错误路径。
```

## 6. 框架完成后交回哪些信息

框架开发者提交的代码、交接记录、实际基线commit和测试结果足够用于下一轮细化。届时根据真实实现删掉已完成任务、明确剩余接口、填写白名单和依赖，再发布可直接执行的三份业务提示词；不用重新讨论已确认的产品需求。
