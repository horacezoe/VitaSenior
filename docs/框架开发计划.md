# VitaSenior 后端框架开发计划

版本：v0.2，2026-10-30。状态：F0公共框架已实现并验收，实际结果与基线见[框架交接记录](协作/框架交接记录.md)；F1/F2业务工作尚未开始。

本文件调整开发顺序：**一个框架 Agent 先建立并验收公共基线，再发布 A/B/C 的业务任务单，随后并行开发。** 当前不要直接用旧分工表启动三人独立搭建后端。

配套：[Agent 开工提示词](Agent开工提示词.md)、[接口说明](后端接口说明.md)、[后端总计划](后端开发计划.md)、[候选分工](三人分工与联调安排.md)、[框架交接记录](协作/框架交接记录.md)。

## 1. 需要先统一什么

并行分支只能避免相互覆盖文件，不能避免两人各自实现不同的字段和服务。因此先统一以下内容：

| 内容 | 框架阶段的交付 | 业务阶段的约束 |
| --- | --- | --- |
| HTTP 契约 | P0 路由、operation_id、Pydantic 请求/响应、错误结构 | 三人沿用同一套 schema，不另造同名 DTO |
| 数据模型 | 所有 P0 表的最小字段、关系、版本字段、必要唯一约束 | 业务 Agent 通过已有模型写业务逻辑；结构变化由集成人统一处理 |
| 身份与权限 | 真实的演示登录、Actor、会话、老人访问检查 | 不使用“永远返回测试老人”的鉴权假函数 |
| 事务与幂等 | 一套 UoW、Session 规则、时钟、幂等存储 | 跨模块一次提交；子服务不自行 commit |
| 跨模块调用 | 类型明确的 ports、输入/输出对象和占位实现 | 只通过 port 调用其他模块；不直接导入对方 service 实现 |
| 应用组装 | create_app、composition、依赖注入和扫描器开关 | 不由三人分别添加第二套应用、调度器或数据库入口 |
| 验收依据 | 实际 OpenAPI 快照、框架测试、交接提交 | 所有分支来自同一基线，合并时检查契约未意外改变 |

## 2. 阶段划分与预算

### F0：单人完成框架

由一位框架开发者或一个编码 Agent 顺序完成。目标投入约 2–3 小时；90 分钟先检查可启动程度。预算计入最初路演剩余时间，不重新计算 38 小时。

其他人此时可准备虚构 fixture、阅读契约和列验收用例，暂不并行修改公共代码或各自建立第二套骨架。若三小时内仍未达到门槛，优先修复启动和共享契约，削减非必要抽象，不继续扩建基础设施。

### F1：验收实际框架并发布任务

依据实际代码审核接口、服务签名、测试和提交记录；补齐交接记录。然后按实际文件路径发布 A/B/C 三份详细任务单、写入白名单和最终启动提示词。

F0 结束后应带回：基线 commit、目录树、OpenAPI 快照、测试结果、未实现项目。详细业务分工在这一步才冻结。

### F2：三人并行补业务

三人从同一个已验收提交建分支或 worktree，使用独立数据库目录。每批完成一个可调用闭环即集成；共享字段改变走约定的变更记录，不在不同分支各自修正。

## 3. 框架需要实际实现的部分

| 任务 | 必须实现 | 验收结果 |
| --- | --- | --- |
| F0-01 | Python 项目、锁定依赖、配置、日志、request_id、错误 envelope、CORS | 空环境可按 README 启动；参数错误也走统一错误结构 |
| F0-02 | SQLite 初始化、SQLAlchemy Base/Session、全部 P0 模型与约束、UoW | 全表能创建；外键启用；写失败时业务数据和幂等记录一起回滚 |
| F0-03 | 可注入 Clock、UTC/HK 日期转换、幂等基础服务 | 测试能推进时钟；重复写请求只产生一次结果；同 key 异体返回 409 |
| F0-04 | SYS01、SYS02、AUTH01、AUTH02、AUTH04 | 五个接口真正可用，登录状态持久化；返回实际能力状态 |
| F0-05 | framework seed：老人、已绑定子女、未绑定子女、另一位老人及会话用数据 | 可验证本人、已绑定、未绑定和陌生老人四种访问范围 |
| F0-06 | 其余 P0 路由与完整请求/响应模型、统一未实现错误 | 有效请求得到 501；字段错误仍为 422，无权限仍为 401/403 |
| F0-07 | ports、ServiceBundle、composition、各领域占位实现 | 启动不报循环导入；所有跨域依赖可替换成测试实现 |
| F0-08 | 可开关扫描器骨架、统一 tick 入口、lifespan 启停 | 测试默认关闭；演示单 worker；只创建一个循环，无真实 60 秒等待 |
| F0-09 | 框架测试、契约导出/检查工具、README、交接记录 | 第 8 节全部通过，记录真实命令、结果和 commit |

框架阶段不要求完成社区导入、绑定码消费、打卡、提醒计算、提案自动应用、Agent 意图和记忆归纳。它们的模型、schema、路由和 port 已就位，业务实现留给 F2。

占位接口不能返回虚假的成功打卡、绑定或 applied 状态。使用 `501 MODULE_NOT_IMPLEMENTED`，并在 runtime.capabilities 中标 false；不得把占位模块报告为已可用。

## 5. 必须冻结的代码约定

### 5.1 数据与 HTTP

- 对外请求/响应只定义在 schemas；枚举只定义在 schemas/enums.py。ORM 表只定义在 models，不能把 ORM 对象直接当 HTTP 响应契约。
- 所有 P0 operation_id 使用接口文档编号；每个成功路由使用有类型的响应模型。媒体二进制接口单独声明，不套 JSON envelope。
- `SourceRef` 统一为 `{type,id,version?}`，只在 schemas/common.py 定义；contracts/context.py 重用它并定义 Actor。Actor 至少含 user_id、role，禁止某模块用 user_id 冒充 elder_id。
- API 文档中没有完全展开的对象，在框架阶段一次补齐 Pydantic 定义及说明；不能用任意 dict 占位后留给三人各自解释。
- 版本、日期、空值、枚举遵循既有接口说明。必要结构性 JSON 字段可以保留，但须有对应的 typed schema，不用扩展 JSON 躲避字段对齐。

### 5.2 事务与跨域调用

- API/application flow 开启事务并负责最终提交；接收 tx 的子服务不得自行 commit、rollback 或另开写 Session。
- Actor 的会话验证与写事务的资源访问检查分清；写操作在实际写事务内再次校验授权，避免用另一条连接上的临时结果替代资源校验。
- 业务写入、动作最终结果、通知回执与修改窗口、幂等成功结果在需要原子性的同一个事务完成。异常回滚后不留下“已确认”但未落库的结果。
- 模型、TTS、转码、文件导出和推送等慢操作在写事务之外；确定性来源失效可在事务内执行。
- 业务模块通过 typed port 调用其他模块；只有 composition 可以组装各模块的具体实现。application flow 可协调多个 port，不直接导入其他领域 service 实现。
- 框架把原接口文档里的简写签名落实为完整参数和返回类型。确认后的实际签名登记到交接记录，后续不靠自然语言猜 tx 的含义。

### 5.3 占位、mock 与能力状态

- 业务尚未实现：501 + capability=false。AI mock 已被 C 真正实现后，才返回 mock 的场景结果。
- mock 仅替换约定的 AI/外部服务，不绕过鉴权、不替代数据库提交、不伪造用户已经服药。
- P1/P2 可以暂不挂载；P0 必须全部出现在 OpenAPI 中。实现进度与业务优先级分开记录。
- framework seed 只用于基础验收；DEMO01 的独立观众家庭、14 天历史导入在 A/B/C 业务阶段完成。

## 6. 公共文件与修改边界

| 类别 | F0 | F2 |
| --- | --- | --- |
| core、models、schemas、contracts | 框架开发者统一创建 | 作为共享基线；由集成人处理契约变更 |
| main、composition、依赖锁、公共测试、seed 总入口 | 框架开发者创建 | 集成人维护；其他人提出明确修改申请 |
| application/identity、对应 services/routers/tests/fixtures | 占位 | A 实现，具体白名单在 F1 发布 |
| application/health、对应 services/routers/tests/fixtures、scheduler | 占位 | B 实现，具体白名单在 F1 发布 |
| application/agent、对应 services/routers/tests/fixtures、providers | 占位 | C 实现，具体白名单在 F1 发布 |

共享文件维护者是团队内部集成人，不需要为每个字段变化再问用户。Agent 发现真实缺口时，写入自己的变更申请并继续其他不依赖该变更的任务；不能私自新增兼容字段或另一套 DTO。

变更申请至少写清：当前基线、实际缺口、涉及字段/签名、兼容性影响、受影响模块和测试。集成人修改一次公共定义、更新快照与基线提交，再通知受影响分支同步。

## 7. 防止并行开发失配的检查

1. 同一基线：F1 记录 Git commit 与 OpenAPI SHA-256。三个分支从此提交创建，不各自 init 一份项目。
2. 契约快照：`export_contract --check` 重新从 app 导出并与已提交快照比较；排序稳定，不把运行时间或随机 token 写进 schema。
3. 导入边界：check_architecture 检查业务 service/application/router 不导入其他领域的 service 实现；composition 为唯一组装入口。发现循环依赖时修复依赖方向。
4. 写入边界：每个 Agent 交付时提供文件清单，核对自己的写入白名单；共享文件差异必须有变更记录。
5. 独立环境：不同 worktree 使用不同 DATA_DIR、SQLite 文件和端口。测试使用 tmp_path，不操作其他人的运行数据。
6. 小步集成：一组可用接口即集成。测试先覆盖跨模块事实一致、权限、回滚和重复请求，再补业务细节。

这些检查应是少量脚本/测试，不引入大型 CI、分布式消息或复杂工作流平台。

## 8. F0_READY 验收门槛

以下命令是**框架需要实现并实际运行**的约定，当前文件没有声明它们已经存在或通过。工作目录为 backend。

```powershell
python -m pytest tests/framework -q
python -m app.tools.export_contract --check
python -m app.tools.check_architecture
```

| 门槛 | 必须验证的事实 |
| --- | --- |
| FG01 | 全 mock/未接供应商密钥时，create_app 可启动；SYS01/SYS02 返回真实状态 |
| FG02 | P0 路由无遗漏、无重复 operation_id；请求/成功响应/统一错误有明确 schema |
| FG03 | 演示登录真实签发会话；未登录、未绑定、陌生老人访问被正确拒绝 |
| FG04 | 空临时 SQLite 可创建所有模型，外键和必要唯一约束实际生效 |
| FG05 | 测试通过人为失败验证整笔事务回滚；幂等重放不重复写，相同 key 异体返回 409 |
| FG06 | FakeClock 可推进过期时间，不真实 sleep；扫描器测试默认不启动后台循环 |
| FG07 | 未实现业务接口返回 501，capabilities 不谎报 true；没有伪造已应用或已打卡的占位结果 |
| FG08 | OpenAPI 快照可重现，检查工具能发现被刻意改变的字段/路由；导入边界检查可发现跨域实现导入 |
| FG09 | framework seed 可重复执行且不破坏已有业务数据；测试目录与运行数据隔离 |
| FG10 | README、真实测试输出、依赖锁、基线 commit、快照 hash、已知缺口已填入交接记录 |

F0_READY 只代表可以分工开发，不代表总计划 AC01–AC14 的业务验收已经完成。

## 9. F1 如何制定最终分工和提示词

框架完成后，以实际代码执行一次检查，再为 A/B/C 各生成一份详细任务单，包含：

1. 确定的基线 commit、角色、目标与不超过一个阶段的任务列表。
2. 实际存在的文件读写白名单、接口编号与服务入口。
3. 已可调用的依赖、明确未实现的依赖，以及允许使用的测试替身。
4. 本角色必须维护的业务不变量、应通过的测试和两侧联调样例。
5. 阶段结束的产物、交接对象、当前限制、具体测试结果。

不能只把“你负责健康模块”发给一个 Agent 就让它自行搭一套。也不在框架尚未完成时编造“这些服务已可调用”。[当前提示词文件](Agent开工提示词.md)中，框架提示词可以立即用于开工；A/B/C 为待 F1 填实的模板。
